# Local browser prototype — movement, choices and robustness

TypeScript + React DOM controls + PixiJS 8 WebGL board over the Java BB2025 engine.
This is a synthetic two-token fixture, not a playable full match or legal roster.
Home starts the turn; the engine assigns each block choice to home or away.
Both see canonical home coordinates: x=0..25, y=0..14 (no away rotation).

## Run locally

From the repository root, in PowerShell:

```powershell
$env:PATH = "$env:LOCALAPPDATA\Programs\DockerDesktop\resources\bin;$env:PATH"
./containers/local/setup.ps1
docker compose -f containers/local/compose.yaml build server
docker compose -f containers/local/compose.yaml up -d --wait
cd browser-client
npm ci
npm run dev
```

Toolchain used: Node 24.19.0, npm 11.17.0; exact package versions and transitive
integrity hashes are in `package-lock.json`. Java stays on the established Java 8
baseline. Node serves/develops the UI only; it is not a second game server.
Vite binds `127.0.0.1:5173`; Compose publishes the JVM only on `127.0.0.1:22227`.

Open two separate browser profiles or private contexts at
[the local client](http://127.0.0.1:5173). In the first, paste the contents of
`containers/local/.secrets/browser_home_token` into the password field; use
`browser_away_token` in the second. These are distinct local bearer credentials
generated by setup, mounted outside the image, and never bundled with the client.
They stay out of URLs and browser persistent storage. Keep them out of screenshots
and logs. The credential determines the role; there is no role selector in join.

The default `BOTH_DOWN` fixture shows a pending choice owned by home. Choose
**Both Down** to resolve both players prone at revision 1. For the original
movement exercise, set `local.browser.fixture=MOVEMENT` and restart the server.
Then select `home-runner`, enter X=6, Y=7, and submit from home. Both views reach revision
1, home-runner at (6,7), movement used 1/6. `Repeat last request` resends the exact
request ID/body and returns its accepted result with `duplicate=true`; it does not
move again. Away submissions and illegal squares are rejected by the server.
The DOM table and request log remain available alongside the Pixi board.

## Verification

```powershell
# From browser-client:
npm test
npm run build
# In a second terminal, with MOVEMENT selected and a fresh server; requires Chrome:
npm run demo
# Optional: $env:BROWSER_CHANNEL = 'msedge' before npm run demo
```

The demo creates two independent browser contexts, reads local credentials without
printing them, joins through the actual UI, checks initial synchronization, tries
wrong-role and illegal moves, makes one adjacent move, repeats it, and submits a
stale wire request. It asserts both views at revision 1 and exactly one movement
broadcast. It records screenshots and sanitized wire traces under
`.notes/overhaul-analysis/verification/m1a/` (`M1A_EVIDENCE` overrides this path).

The demo requires a fresh fixture. Reset **only the in-memory browser fixture** by
restarting the local server before running it again:

```powershell
docker compose -f containers/local/compose.yaml restart server
docker compose -f containers/local/compose.yaml up -d --wait
```

This is an operator command, not a browser endpoint. It preserves MariaDB/backup
volumes and existing M0b matches; it interrupts active local sessions. The M1a
fixture, revision and dedupe history are in memory and reset on JVM restart.
Disconnect/rejoin without a JVM restart restores the complete pending decision.
Restart is a new fixture lifetime, with a new match ID and empty retry history.

## Controlled M1b acceptance

Set `local.browser.fixture` in `containers/local/server.ini` to `BOTH_DOWN`,
`BOTH_DOWN_BLOCK`, `BOTH_DOWN_AWAY`, or `BOTH_DOWN_AWAY_BLOCK`. The default is
`BOTH_DOWN`. `MOVEMENT` retains the M1a movement demo. These are local operator
controls, outside the browser protocol. Rebuild the server after source changes,
and restart it after changing the fixture property. Invalid fixture names fail
startup. No database reset is needed.

Block fixtures begin paused at a Both Down decision. Home/away observe the same
prompt and canonical coordinates; only the prompt owner can select an option.
Use **Disconnect**, re-enter the same credential, and join to restore the full
current snapshot. **Repeat last request** explicitly retries the cached choice,
including after a lost acknowledgement; there is no automatic replay. Reloading
the page loses that cached request but still restores the current pending choice.

From `browser-client`, after restarting with the selected fixture:

```powershell
$env:M1B_FIXTURE = 'BOTH_DOWN'
$env:M1B_EVIDENCE = '../.notes/overhaul-analysis/verification/m1b/BOTH_DOWN'
npm run demo:choice
```

Repeat for all four variants, restarting the server each time. The driver uses
two browser contexts and the rendered controls. It verifies pending disconnect
recovery, wrong-owner rejection, dropped acknowledgement/snapshot recovery,
engine-derived player states and explicit idempotent retry. It writes screenshots
and sanitized wire evidence without credentials. M1a's `npm run demo` requires
`MOVEMENT` and a fresh revision-zero fixture.

Full Java verification remains `./tools/build.ps1 install -Offline` followed by
`./tools/build.ps1 verify -Offline` from the root. See the kickoff status for the
actual run results and [protocol](protocol.md) for wire semantics.

## Scope

Supported intents are adjacent, unoccupied, in-bounds movement without dice in
the movement fixture, and selecting one server-owned option in a block fixture.
The engine executes the accepted command; React/Pixi never calculate game results.
No block-start, dice, scenario-loader, reset, match-create or arbitrary legacy command
exists in the browser schema. Local startup owns fixture construction. M1b covers
these controlled block decisions/reconnect; M1c verifies failure paths, repeat-action metrics,
expanded protocol fixtures and closeout. Both are complete for this narrow prototype. Java 21 and public service policy remain
later milestones.

Implementation references checked when pinning dependencies:
[Vite requirements](https://vite.dev/guide/) and
[PixiJS Application initialization](https://pixijs.com/8.x/guides/components/application).

## M1c robustness and repeatable acceptance

The diagnostic marker is a local SVG decoded into a Pixi texture. Missing mapping
or failed load uses labeled `F H` / `F A` tokens and a status message; selection,
movement, authoritative state and request results remain usable. There is one
load attempt per board lifetime, with no per-frame retry. WebGL initialization
failure displays an actionable message. DOM gameplay controls remain usable;
enable hardware acceleration and reload to restore the board. There is no Canvas
fallback. Development-only `rendererFault=missing-asset-mapping` or
`rendererFault=asset-load-failure` query configuration is for the test harness;
it is ignored in the production build and never sent to the server.

The local configuration explicitly enables `/tmp/ffb-browser-control` as an
operator file mailbox inside the container. It accepts one bounded request at a
time through container filesystem access. It is not an HTTP endpoint and does not
use or replace gameplay credentials. The helper below atomically writes a request
and waits for the matching response. Reset interrupts local browser sessions and
replaces only the in-memory fixture; database/backup volumes are preserved.
The `hold` operator operation occupies the communication worker for exactly one
second after a `phase:holding` acknowledgement. It is a bounded saturation-test
fault, never a gameplay command and never used in the latency workload.

```powershell
# From browser-client, with the final M1c image and Vite running:
node test/m1c-local.mjs reset MOVEMENT
node test/m1c-local.mjs metrics
$env:M1A_EVIDENCE = '../.notes/overhaul-analysis/verification/m1c/movement'
npm run demo
# Reset to each of BOTH_DOWN, BOTH_DOWN_BLOCK, BOTH_DOWN_AWAY, BOTH_DOWN_AWAY_BLOCK:
node test/m1c-local.mjs reset BOTH_DOWN
$env:M1B_FIXTURE = 'BOTH_DOWN'
$env:M1B_EVIDENCE = '../.notes/overhaul-analysis/verification/m1c/BOTH_DOWN'
npm run demo:choice
npm run demo:renderer-failures
npm run demo:renderer-lifecycle
node test/robustness-demo.mjs
node test/workload-demo.mjs
```

The workload keeps one browser and JVM running across two warm-up and 100 measured
fixture lifetimes. Six legal engine moves per lifetime respect movement allowance;
two rejected actions, two exact retries and one reconnect complete each measured
lifetime. The 1,000 submissions therefore include 600 mutations, not 1,000.
The final retirement restores a fresh `BOTH_DOWN` fixture. See
[M1c evidence](../.notes/overhaul-analysis/verification/m1c/README.md) for results,
limitations, source/image identity and full reproduction commands.
