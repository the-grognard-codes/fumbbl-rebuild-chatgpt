## BB2025 dispatch

Rules variants are selected with `@RulesCollection`, factories and classpath discovery. Server construction creates/initializes a `FactoryManager` ([FantasyFootballServer.java:90](../../ffb-server/src/main/java/com/fumbbl/ffb/server/FantasyFootballServer.java#L90)); common uses ClassGraph in `ScannerSingleton` ([ScannerSingleton.java:11](../../ffb-common/src/main/java/com/fumbbl/ffb/util/ScannerSingleton.java#L11)). BB2025 code spans common skills/mechanics/model, server steps/generators/behaviours and client interaction states. Startup explicitly sets the game option to BB2025 ([UtilServerStartGame.java:227](../../ffb-server/src/main/java/com/fumbbl/ffb/server/util/UtilServerStartGame.java#L227)).

**Recommendation (inferred):** retain this arrangement while proving a web vertical slice. The common/server engine has no AWT/Swing import dependency. Improve scanner registration or engine shape only if a concrete issue—web bundle boundary, startup, reproducibility or test isolation—demonstrates the need. Apply the repository rule against cross-ruleset inheritance whenever BB2025 behavior changes.

## Findings and actions

**Priority A — prove the thin web route without changing rules execution.** A web endpoint can translate intents into current server commands, consume current model/report updates, and expose browser DTOs. The first route should cover local roster selection, setup, move, block/reroll, pass/turnover, score/end and replay. That validates actual UX and projection needs before any executor, persistence, or dispatch rewrite.

**Priority A — isolate external lifecycle side effects incrementally.** `StepEndGame` chooses FUMBBL upload versus replay save ([StepEndGame.java:59](../../ffb-server/src/main/java/com/fumbbl/ffb/server/step/game/end/StepEndGame.java#L59)), while BB2025 end-turn conditionally updates FUMBBL state ([StepEndTurn.java:765](../../ffb-server/src/main/java/com/fumbbl/ffb/server/step/bb2025/StepEndTurn.java#L765)). Put a `MatchLifecycle`/storage adapter at those points and preserve the current default behavior. It is lower risk than changing rules sequences.

**Priority B — convert named gaps into scenario tests.** The existing tests cover useful fragments, especially block, injury, hand-off turnover, Safe Pass, On the Ball/pass block, reroll API and Swarming end turn. The matrix specifies the missing cases that should become named tests before each web feature is advertised. Test the current command/step boundary first; then test that browser adapters do not alter outcomes.

**Priority B — do not create browser rules duplication.** Client/server duplication largely concerns interaction and legacy wire UI; it is not an AWT import dependency in the engine. Browser client should request/render legal actions and targets from authoritative server state, not independently implement BB2025 legality.

**Priority C — defer structural rewrites.** ClassGraph registration, mutable `GameState`, stack steps, legacy command JSON and snapshot/log persistence constrain evolution, but inspection did not show any one blocks a browser proof. Record concrete evidence—startup trouble, unsafe restoration, impossible DTO projection, or untestable extension—before replacing them.

## Behavior boundaries worth preserving in tests

The engine distinguishes a client proposal from a model update in ways a browser adapter must not accidentally flatten. Move validation checks the actor and a supplied path, but `StepMove` computes actual state after that validation. Pass dispatch takes target coordinate only after action/actor checks and `StepEndPassing` makes the turnover decision after the pass/catch sequence. Blocking first captures the requested defender, then makes defender state and action changes before dice/push/injury steps. The implication is modest but important: browser messages should remain intent-level and be rejected without state change when a server step does not accept them; browser rendering should treat server synchronization as authoritative.

The current stack also carries deferred decisions. `StepInitBlocking` can publish `OLD_DEFENDER_STATE`, defender position and weapon flags to later steps ([StepInitBlocking.java:225](../../ffb-server/src/main/java/com/fumbbl/ffb/server/step/bb2025/block/StepInitBlocking.java#L225)); `StepEndPassing` preserves catcher/interceptor/fumble/end-turn parameters through its state ([StepEndPassing.java:77](../../ffb-server/src/main/java/com/fumbbl/ffb/server/step/bb2025/pass/StepEndPassing.java#L77)). A DTO adapter needs explicit representations for “choose now” dialogs and legal target/range information, or it will incorrectly force rules decisions into the client. No engine rewrite is required to model this: map the existing step/dialog output first and characterize behavior with state tests.

## Suggested characterization sequence

Start with one deterministic scenario per matrix row and store its expected observable sequence: accepted/rejected input, model location/state, turn owner/mode, reports, dialog prompt and replay output. Then add variations around the decision boundary: wrong actor, stale action, unavailable reroll, opponent intercept, ball entering end zone, session reconnect and late spectate. The test driver already contains `TestServer`, `StepEngine`, `GameStateBuilder` and `Commands` sources under `ffb-statetest`; use them as the starting harness rather than inventing a parallel rules simulator.

For browser integration, use a separate contract suite that submits the same intents through the web adapter and compares the normalized server result to the engine-boundary scenario. This makes a web rendering defect distinguishable from a rules regression. It also lets the legacy desktop client stay available as a reference while browser functionality grows incrementally.

## Ruleset and product scope choices

BB2025 should be an explicit supported match type in the local catalog rather than merely the default string assigned at startup. The first browser release can intentionally exclude historical BB2016/BB2020 lobby choices, FUMBBL division management, remote result submission, managed league progression and 3D. Exclusion from the product scope is not deletion from the repository: existing ruleset classes and integration code can remain untouched until there is a demonstrated need to split build artifacts or reduce maintenance cost.

Roster building merits its own contract because current local team XML and remote roster loading solve different problems. A web builder needs a catalog/version, allowed positions, budget and quantity validation, selected skills/advances where supported, a stable roster ID, and a frozen roster snapshot for a match. The audit has not verified that the existing XML examples form a complete BB2025 catalog; treat import/conversion as a discovery task and show unsupported roster configurations clearly.

## Unproven material gaps

1. No inspected test establishes full BB2025 parity; annotated class presence is not compliance certification.
2. No inspected test establishes browser projection correctness, recipient privacy, reconnect recovery, or duplicate-command behavior.
3. No runtime inspection establishes successful standalone startup with supplied local DB or confirms all remote calls are inactive in standalone mode.
4. Asset licensing/provenance, roster-data completeness, and deployed TLS/auth configuration are outside this code-path audit.

These are decision gates for expansion beyond the first web vertical slice, not grounds to discard the existing engine.
